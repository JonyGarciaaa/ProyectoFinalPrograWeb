1. Resumen Ejecutivo y Enlaces Oficiales

1.1 Problemática y Justificación: En las instituciones de educación superior, la reserva de aulas ejecutivas, auditorios, salones para dinámicas y laboratorios especializados tradicionalmente ha dependido de procesos manuales (solicitudes por correo electrónico, llamadas telefónicas o anotaciones en hojas de cálculo). Dichos métodos propician errores frecuentes como doble reservación para un mismo espacio, poca claridad respecto a la disponibilidad real en un día determinado y falta de auditoría sobre quién autorizó o canceló una actividad.

ReserveHub fue diseñado y desarrollado para sustituir estos mecanismos por una solución web automatizada, moderna y segura, dotada de verificación algorítmica de solapamiento en tiempo real, autenticación basada en estándares y arquitectura multicapa desacoplada.

2.1 Justificación Técnica del Stack Seleccionado

  • React 19 y TypeScript: Proporciona tipado estático en el frontend, previniendo errores de renderizado en tiempo de compilación. La estructura por componentes modulares garantiza una interfaz interactiva y accesible sin requerir plantillas prediseñadas.
  • Express 5 y Node.js 22: Facilita el desarrollo de una API REST asíncrona de alto rendimiento, con soporte nativo de promesas en manejadores de ruta y middlewares modulares.
  • Prisma ORM y PostgreSQL: Abstrae el acceso a la base de datos asegurando tipado de extremo a extremo, generación declarativa de migraciones y protección implícita contra inyecciones SQL mediante sentencias parametrizadas.
  • Vite y Tailwind CSS: Empaquetador de última generación con recarga ultrarrápida y framework de utilidades CSS que permite diseñar interfaces responsivas limpias y con semántica accesible (WCAG).

3. Modelo de Base de Datos y Persistencia

La base de datos relacional se compone de cuatro entidades principales diseñadas bajo la tercera forma normal (3NF):

Tabla Campos Clave Relaciones Propósito
users id (UUID PK), email (Unique), password, role (Enum) 1 a N con reservations Almacena cuentas de usuario con rol USER o ADMIN y contraseñas cifradas en bcrypt.
spaces id (UUID PK), name, capacity, location, status (Enum) 1 a N con reservations y schedules Catálogo de instalaciones universitarias con capacidad y estado (ACTIVE / INACTIVE).
reservations id (UUID PK), userId (FK), spaceId (FK), reservationDate, startTime, endTime, status (Enum) N a 1 con users y spaces (onDelete: Cascade) Registros de reserva con fecha (YYYY-MM-DD), rango horario y estado del ciclo de vida.
schedules id (UUID PK), spaceId (FK), dayOfWeek (0-6), openingTime, closingTime N a 1 con spaces (onDelete: Cascade) Horarios de apertura y cierre configurados para cada día de la semana.

Optimización mediante Índices: Se incorporó un índice compuesto sobre [spaceId, reservationDate] en la tabla reservations, permitiendo que la verificación de disponibilidad y detección de colisiones se ejecute en tiempo logarítmico O(log N) sin importar el volumen histórico de reservaciones acumuladas.

4. Reglas de Negocio y Algoritmo Anti-Solapamiento

4.1 Fundamento Matemático del Algoritmo Anti-Solapamiento (RN-01)

Dos intervalos de tiempo A = [t1, t2] y B = [t3, t4] se solapan si y solo si el inicio del nuevo intervalo ocurre antes de la finalización del intervalo existente, y la finalización del nuevo intervalo ocurre después del inicio del existente:

Condición de Conflicto: (nueva_inicio < existente_fin) AND (nueva_fin > existente_inicio)

Implementación en el servicio backend (backend/src/services/reservationService.ts):

const existingConflicts = await prisma.reservation.findMany({
  where: {
    spaceId: data.spaceId,
    reservationDate: data.reservationDate,
    status: { in: ['CONFIRMED', 'PENDING'] },
    AND: [
      { startTime: { lt: data.endTime } },
      { endTime: { gt: data.startTime } },
    ],
  },
});

if (existingConflicts.length > 0) {
  throw new AppError(
    `Conflicto de horarios (RN-01): El espacio ya se encuentra reservado ` +
    `en el rango solicitado (${existingConflicts[0].startTime} - ${existingConflicts[0].endTime}).`,
    409
  );
}

4.2 Resumen de las 9 Reglas de Negocio Implementadas

Código Regla de Negocio Mecanismo de Control en el Sistema
RN-01 Sin conflicto de horarios simultáneos. Query condicional de intervalo abierto en Prisma con código HTTP 409.
RN-02 Autenticación obligatoria para reservar. Middleware authenticateToken verificando firma del JWT.
RN-03 Cancelación restringida a reservas propias. Validación de req.user.userId === reservation.userId en el servicio.
RN-04 Administración total de reservas. Rutas protegidas con middleware requireAdmin.
RN-05 Bloqueo de espacios inactivos. Validación de space.status === 'ACTIVE' antes de confirmar.
RN-06 Coherencia temporal en horarios. Esquema Zod con regla .refine(data => data.startTime < data.endTime).
RN-07 Restricción de reservas en fechas pasadas. Validación comparativa contra la fecha actual ISO (YYYY-MM-DD).
RN-08 Integridad referencial usuario-espacio. Llaves foráneas con validación de existencia previa en base de datos.
RN-09 Ciclo de vida de la reservación. Enum estricto: PENDING, CONFIRMED, CANCELLED, COMPLETED.

5. Seguridad Aplicada basada en OWASP Top 10

  • A01: Broken Access Control (Control de Acceso): Implementación de RBAC (Role-Based Access Control). Los usuarios generales solo pueden interactuar con sus propios recursos. Rutas críticas de creación de espacios y auditoría global exigen rol ADMIN verificado criptográficamente en el payload del JWT.
  • A02: Cryptographic Failures (Cifrado y Credenciales): Ninguna contraseña se almacena en texto plano. Se procesan con bcryptjs empleando 10 rondas de salting aleatorio. Los tokens JWT se firman con el algoritmo HMAC-SHA256 con clave secreta inyectada por variable de entorno y tiempo de expiración definido (7 días).
  • A03: Injection (Inyecciones SQL y NoSQL): Al utilizar Prisma ORM, todas las consultas a PostgreSQL se ejecutan como sentencias preparadas y parametrizadas, neutralizando cualquier intento de inyección de código SQL malicioso.
  • A04: Insecure Design (Validación de Entradas): Todos los endpoints procesan el cuerpo de la petición (req.body), parámetros de ruta (req.params) y cadenas de consulta (req.query) contra esquemas estrictos de Zod. Cualquier payload anómalo es descartado de inmediato con respuesta HTTP 400.
  • A05: Security Misconfiguration (Configuración Segura): Se configuró el middleware helmet, estableciendo cabeceras HTTP como X-Content-Type-Options: nosniff, X-Frame-Options: SAMEORIGIN y políticas de protección contra Clickjacking y XSS.

8. DevOps, Contenerización y Flujo CI/CD

8.1 Contenerización con Docker y Docker Compose

La solución se encuentra completamente contenerizada. El archivo docker-compose.yml define tres servicios interconectados a través de una red interna aislada:

  • reservehub-postgres: Contenedor basado en la imagen ligera postgres:16-alpine con volumen montado (pgdata) para garantizar persistencia física de los datos.
  • reservehub-backend: Construido con un Dockerfile multi-etapa en Node 22 que compila TypeScript, ejecuta automáticamente npx prisma db push y el sembrado de datos (seed) al iniciar, exponiendo el puerto 4000.
  • reservehub-frontend: Construido con un Dockerfile multi-etapa que compila los assets estáticos con Vite y los sirve a través de un servidor web Nginx Alpine en el puerto 5173 con compresión gzip y soporte para rutas SPA.

Comando de Ejecución Local en 1 Paso:

docker compose up -d --build

8.2 Pipeline de Integración Continua (GitHub Actions)

En el archivo .github/workflows/ci.yml se configuró una canalización automática que se ejecuta en cada push hacia la rama main:

  1. Levanta un contenedor de servicio temporal de PostgreSQL 16 con verificación de salud (healthcheck).
  2. Instala dependencias con verificación estricta de lockfile (npm ci).
  3. Aplica el esquema de Prisma y ejecuta el script de sembrado de datos en la base de pruebas.
  4. Ejecuta el compilador de TypeScript (tsc) asegurando cero errores de tipos.
  5. Ejecuta la suite de pruebas de integración de backend con Vitest.
  6. Compila el frontend con Vite y ejecuta las pruebas de componentes.

9. Guía de Preguntas Técnicas para la Defensa del Proyecto

P1: ¿Cómo garantizan que dos usuarios no reserven el mismo salón a la misma hora simultáneamente?
R: Mediante dos barreras: en la capa de servicio del backend, antes de escribir en la base de datos se ejecuta una consulta con filtro de solapamiento de intervalos (inicio_nuevo < fin_existente AND fin_nuevo > inicio_existente) sobre reservas confirmadas y pendientes. Si existe colisión, la operación se cancela arrojando un error 409 Conflict. A nivel de base de datos, las transacciones de Prisma aseguran atomicidad en la inserción.
P2: ¿Cómo evitan que un usuario común altere o elimine reservas de otros usuarios o cree salones?
R: Empleamos control de acceso basado en roles (RBAC). El token JWT contiene en su payload el ID del usuario y su rol ('ADMIN' o 'USER') firmado con una clave secreta del servidor. En rutas administrativas (como POST/PUT en /spaces) se antepone el middleware requireAdmin. En la cancelación de reservas, el servicio compara estrictamente si user.role !== 'ADMIN' && reservation.userId !== user.userId, rechazando con código 403 Forbidden cualquier intento no autorizado.
P3: ¿Por qué se utilizó Prisma ORM en lugar de escribir consultas SQL tradicionales?
R: Prisma aporta tres ventajas de ingeniería: 1) Tipado estático completo sincronizado con TypeScript (si cambia una columna en la base de datos, el código que la consuma no compilará hasta corregirse); 2) Prevención nativa de SQL Injection mediante consultas parametrizadas automáticas; y 3) Portabilidad y migraciones declarativas que permiten ejecutar el mismo esquema en PostgreSQL local (Docker) o en PostgreSQL en la nube (Render).
P4: ¿Cómo se asegura la persistencia de datos en Docker si se apagan los contenedores?
R: En el archivo docker-compose.yml se definió un volumen nombrado (pgdata) mapeado hacia el directorio interno /var/lib/postgresql/data del contenedor de base de datos. Por ende, los datos físicos residen en el disco de la máquina anfitriona y sobreviven a reinicios o reconstrucciones de los contenedores.
